프론트는 화면이 깨져도 새로고침하면 다시 시작할 수 있는데, 서버는 데이터가 꼬이는 순간 새로고침으로 해결이 안 된다. 거기다 한 명이 아니라 여러 명이 동시에 같은 버튼을 누르기 시작하면서부터 신경 써야 할 것들이 확 늘어난다.

이 글에서는 백엔드를 처음 맡았을 때 자주 터지는 문제들을 **DB, 인프라, 보안** 순으로 짚어보고, 뒤에 **트래픽이 몰릴 때와 장애가 났을 때** 실제로 어떻게 움직이는지 정리했다.

---

## 1. DB

코드는 잘못 짜면 고쳐서 다시 배포하면 그만이지만, 잘못 들어간 데이터는 누가 수동으로 복구하기 전까지 계속 남는다. 그래서 데이터 무결성을 지키는 장치는 최대한 DB 가까운 곳에 둬야 한다.

### 검증은 앱에서 하더라도 보장은 DB에서 한다

이메일 중복을 막는다고 흔히 이렇게 코드를 짠다.

```ts
const exists = await db.user.findUnique({ where: { email } });
if (exists) throw new Error("이미 가입된 이메일입니다");
await db.user.create({ data: { email, name } });
```

혼자 테스트할 땐 아무 문제 없다. 근데 사용자가 가입 버튼을 따닥 누르거나 요청 두 개가 거의 동시에 들어오면, 둘 다 `findUnique`를 통과한 뒤 `create`를 실행하면서 같은 이메일 계정이 두 개 생긴다. 조회와 생성 사이에 빈틈이 있기 때문이다.

동시 요청까지 막아주는 건 결국 DB 제약조건이다.

```sql
ALTER TABLE users ADD CONSTRAINT users_email_key UNIQUE (email);
```

이렇게 걸어두면 두 번째 `INSERT`는 DB가 막아준다. 앱 코드는 그 에러를 잡아서 친절한 안내 메시지로 바꿔 내려주기만 하면 된다. 마찬가지로 비어 있으면 안 되는 컬럼은 `NOT NULL`, 참조 관계는 외래 키(FK), 허용 범위는 `CHECK`(`CHECK (stock >= 0)` 같은 식)로 DB에 직접 박아두는 게 안전하다.

ORM을 쓴다면 스키마에 선언하고 마이그레이션으로 반영한다.

```prisma
model User {
  id    Int    @id @default(autoincrement())
  email String @unique   // UNIQUE
  name  String           // ?가 없으면 NOT NULL
}
```

주의할 점은 앱 레벨 유효성 검사(`validate`, DTO 검증 데코레이터 등)와 DB 제약조건을 헷갈리는 것이다. 앱 단 검증은 입력 형식을 거르는 용도지 동시성까지 막아주지 못한다. 또 Prisma처럼 스키마 문법으로 `CHECK`를 못 쓰거나 `relationMode = "prisma"` 설정으로 실제 FK를 끄는 경우도 있으니, 생성된 마이그레이션 SQL을 눈으로 확인하는 습관을 들이는 게 좋다.

### 한 세트로 움직여야 하면 트랜잭션으로 묶는다

포인트 결제 후 주문 내역을 만드는 로직을 따로 실행한다고 해보자.

```ts
await db.user.update({ where: { id: userId }, data: { points: { decrement: price } } });
await db.order.create({ data: { userId, productId, price } }); // 여기서 터지면?
```

두 번째 줄에서 에러가 나거나 서버가 재시작되면 포인트만 차감되고 주문은 생성되지 않는다. 둘 다 성공하거나 둘 다 실패해야 하는 작업은 트랜잭션으로 묶는다.

```ts
await db.$transaction(async (tx) => {
  await tx.user.update({ where: { id: userId }, data: { points: { decrement: price } } });
  await tx.order.create({ data: { userId, productId, price } });
});
```

트랜잭션 내부에서 예외가 발생하면 앞선 변경 사항까지 전부 롤백된다. 단, **트랜잭션 안에서 외부 API(결제 대행사 승인, 알림 발송 등)를 호출하는 건 피해야 한다.** 외부 응답을 기다리는 몇 초 동안 DB 커넥션과 락을 계속 물고 있게 되고, 외부 시스템에서 이미 처리된 작업은 DB 롤백으로 되돌릴 수도 없다.

### 읽고 나서 계산해 덮어쓰는 코드를 조심한다

한정판 재고를 줄이는 코드에서 이런 실수가 자주 나온다.

```ts
const product = await db.product.findUnique({ where: { id } });
if (product.stock <= 0) throw new Error("품절");
await db.product.update({ where: { id }, data: { stock: product.stock - 1 } });
```

재고가 1개 남았을 때 두 명이 동시에 주문하면 둘 다 `stock = 1`을 읽은 뒤 각각 `0`으로 덮어쓴다. 물건은 하나인데 주문이 두 건 잡힌다.

값을 메모리로 가져와서 계산한 뒤 다시 쓰는 대신, 조건을 포함해 단일 쿼리로 갱신하는 게 훨씬 안전하다.

```sql
UPDATE products SET stock = stock - 1 WHERE id = $1 AND stock > 0;
```

영향받은 행(affected rows)이 0개면 품절 처리하면 된다. 계산 로직이 복잡해서 쿼리 하나로 안 될 때는 트랜잭션 안에서 `SELECT ... FOR UPDATE`로 대상 행을 잠근 뒤 처리하고, `CHECK (stock >= 0)`를 최후의 안전장치로 둔다. 로컬 단독 테스트에선 절대 안 보이는 버그라 "읽은 값으로 다시 쓰는 패턴"이 보이면 일단 의심부터 해봐야 한다.

### 같은 요청이 두 번 와도 결과는 한 번만 나오게 한다

결제 요청이 서버에 두 번 들어오는 건 생각보다 흔하다. 버튼 연타도 있지만, 모바일 네트워크가 잠깐 끊겼다가 앱이 재시도하거나 응답이 늦어 사용자가 새로고침하는 경우도 많다. 대비가 안 돼 있으면 주문도 두 건, 결제도 두 번 나간다.

조회는 여러 번 해도 상관없지만 결제·송금처럼 중복 실행되면 안 되는 요청은 멱등성(idempotency)을 보장해야 한다. 보통 클라이언트가 요청마다 고유 키(`Idempotency-Key`)를 생성해 헤더로 보내고, 서버가 이를 DB의 `UNIQUE` 컬럼에 주문과 함께 저장하는 방식을 쓴다.

```ts
// 결제 화면 진입 시 한 번 생성하고, 재시도할 때도 같은 값을 보낸다
const idempotencyKey = crypto.randomUUID();

fetch("/api/orders", {
  method: "POST",
  headers: { "Idempotency-Key": idempotencyKey },
  body: JSON.stringify({ productId }),
});
```

같은 키로 두 번째 요청이 들어오면 `UNIQUE` 제약에 걸려 `INSERT`가 실패하므로, 새로 처리하지 않고 처음 만들어진 주문을 그대로 돌려준다. Stripe 같은 결제 API들이 이 방식을 쓴다. 프론트에서 버튼을 `disabled` 처리하는 건 더블클릭 정도만 막을 뿐 네트워크 재시도까지는 막지 못한다.

### 루프 안에서 쿼리 날리는 N+1 패턴

게시글 목록에 작성자 이름을 붙이려고 이렇게 짜기 쉽다.

```ts
const posts = await db.post.findMany({ take: 20 });
for (const post of posts) {
  post.author = await db.user.findUnique({ where: { id: post.authorId } });
}
```

목록 조회 1번에 작성자 조회 20번, 총 21번의 쿼리가 나간다. 데이터가 적을 땐 티가 안 나다가 댓글·좋아요까지 붙기 시작하면 페이지 하나 띄울 때 쿼리가 수백 번씩 나간다. `JOIN`이나 ORM의 `include` 등을 써서 한 번에 묶어 가져와야 한다.

```ts
const posts = await db.post.findMany({ take: 20, include: { author: true } });
```

ORM을 쓰면 코드만 봐서는 실제 쿼리가 몇 번 나가는지 놓치기 쉽다. 로컬 개발 환경에서는 쿼리 로그를 켜두고, 화면 하나 열었는데 로그가 스크롤을 넘어가면 N+1부터 의심하는 게 좋다.

### 인덱스

데이터가 천 건일 땐 뭘 어떻게 짜도 빠르다. 10만 건, 100만 건이 넘어가는 순간 갑자기 느려지는데 대부분 인덱스 문제다. 인덱스가 없으면 `WHERE email = ...` 하나 찾으려고 테이블 전체를 처음부터 끝까지 읽는다(Full Table Scan).

```sql
CREATE INDEX posts_author_id_created_at_idx ON posts (author_id, created_at);
```

인덱스는 `WHERE`, `JOIN`, `ORDER BY`에 자주 걸리는 컬럼 위주로 잡는다. PK와 `UNIQUE` 컬럼엔 자동 생성되지만, PostgreSQL 같은 DB는 외래 키 컬럼에 인덱스를 자동으로 만들어주지 않으니 직접 걸어야 한다. 쿼리가 느릴 땐 앞에 `EXPLAIN ANALYZE`를 붙여 실행 계획을 확인하고, `Seq Scan`이 보이면 인덱스를 검토한다. 다만 인덱스가 많을수록 `INSERT`·`UPDATE` 때마다 인덱스도 같이 갱신해야 해서 쓰기 성능이 떨어지므로 필요한 쿼리에 맞춰 걸어야 한다.

### 목록 API에는 반드시 끝을 둔다

조건 없이 `findMany()`를 부르는 API는 초기 데이터가 50건일 땐 멀쩡하다. 1년 뒤 50만 건이 되면 응답 한 번에 수십 MB가 실리면서 서버 메모리가 터진다. 목록 API에는 처음부터 개수 제한과 페이지네이션을 넣어야 한다.

`OFFSET` 기반 페이지네이션은 구현은 쉽지만 뒤쪽 페이지로 갈수록 앞선 행을 다 세고 버려야 해서 느려진다. 무한 스크롤 같은 UI라면 마지막으로 받은 항목을 기준으로 다음 묶음을 가져오는 **커서(cursor) 기반 페이지네이션**이 훨씬 유리하다.

```http
GET /api/posts?limit=20
→ { "items": [...20개], "nextCursor": 981 }

GET /api/posts?limit=20&cursor=981
→ { "items": [...20개], "nextCursor": 958 }

GET /api/posts?limit=20&cursor=12
→ { "items": [...7개], "nextCursor": null }
```

```ts
const limit = Math.min(Number(req.query.limit) || 20, 100);
const cursor = req.query.cursor ? Number(req.query.cursor) : undefined;

const posts = await db.post.findMany({
  where: cursor ? { id: { lt: cursor } } : undefined,
  orderBy: { id: "desc" },
  take: limit + 1, // 다음 페이지 존재 여부를 확인하려고 1개 더 조회
});

const hasNext = posts.length > limit;
const items = posts.slice(0, limit);
res.json({ items, nextCursor: hasNext ? items[items.length - 1].id : null });
```

```sql
SELECT * FROM posts
WHERE id < 981
ORDER BY id DESC
LIMIT 21;
```

PK 인덱스를 타기 때문에 몇 번째 페이지를 조회하든 속도가 일정하고, 중간에 새 글이 올라와도 `OFFSET`처럼 목록이 밀려 중복 노출되는 일이 없다. `created_at`처럼 값이 겹칠 수 있는 컬럼으로 정렬할 때는 `(created_at, id)` 조합을 커서로 써야 경계에서 데이터가 누락되거나 겹치지 않는다.

```sql
WHERE (created_at, id) < ($1, $2)
ORDER BY created_at DESC, id DESC
```

### 돈과 시간 타입

금액 계산에 `float`를 쓰면 안 된다. 자바스크립트에서 `0.1 + 0.2`가 `0.30000000000000004`가 나오는 것처럼 부동소수점 오차가 생긴다. 원화면 원 단위 정수로, 소수점이 있는 통화면 센트 단위의 정수나 DB의 `NUMERIC` 타입으로 저장한다.

시간은 무조건 UTC(`timestamptz`)로 저장하고, 한국 시간(KST) 변환은 클라이언트에 보여줄 때 처리한다. "오늘 가입자 수" 같은 집계 쿼리도 어느 타임존 기준의 '오늘'인지 명확히 잡아야 매일 아침 9시에 날짜가 바뀌는 참사를 피할 수 있다.

### 스키마 마이그레이션은 한 번에 밀어붙이지 않는다

프론트는 배포가 잘못되면 이전 버전으로 롤백하면 끝이지만, DB 스키마는 컬럼을 날리는 순간 데이터도 같이 날아간다. 또 배포 중에는 구버전 서버와 신버전 서버가 잠깐 공존하기 때문에 컬럼 변경이나 삭제는 단계를 쪼개서 진행해야 한다.

**컬럼 이름 변경 / 삭제 순서:**

1. 새 컬럼을 추가한다.
2. 앱 코드가 구 컬럼과 신 컬럼 양쪽에 모두 쓰도록 배포한 뒤, 기존 데이터를 백필(backfill)한다.
3. 읽기를 신 컬럼으로 전환해 배포한다.
4. 구 컬럼을 참조하는 코드가 전혀 없는 걸 확인한 뒤 삭제한다.

**기존 테이블에 `NOT NULL` 컬럼 추가 순서:**
처음부터 `NOT NULL`로 추가하면 기존 행 때문에 마이그레이션이 실패한다.

1. 우선 `nullable`로 추가한다. (`ALTER TABLE users ADD COLUMN nickname text;`)
2. 신규 가입·수정 시 `nickname`을 채우는 코드를 배포한다.
3. 기존 행을 몇천 건씩 나눠서 채운다. 수백만 건을 한 번에 `UPDATE`하면 테이블 락과 부하가 치솟는다.

   ```sql
   UPDATE users SET nickname = split_part(email, '@', 1)
   WHERE id BETWEEN 1 AND 5000 AND nickname IS NULL;
   -- 5001~10000, 10001~15000 ... 순차 실행
   ```

4. `NULL`이 0건인지 확인한 뒤 `NOT NULL`을 건다.

   ```sql
   SELECT count(*) FROM users WHERE nickname IS NULL;
   ALTER TABLE users ALTER COLUMN nickname SET NOT NULL;
   ```

*(대용량 PostgreSQL 테이블이라면 `SET NOT NULL`이 쓰기를 막으므로 `CHECK (nickname IS NOT NULL) NOT VALID`로 먼저 걸고 `VALIDATE CONSTRAINT`로 무중단 검증하는 방식을 쓴다.)*

물론 `plan text NOT NULL DEFAULT 'free'`처럼 고정 기본값이 있는 컬럼은 PostgreSQL 11 이상에서 테이블 재작성 없이 바로 추가된다. 반면 `gen_random_uuid()`처럼 행마다 값이 달라지는 기본값은 전체 테이블을 다시 쓰므로 주의해야 한다.

또한 `ALTER TABLE`은 잠깐이라도 테이블 전체 잠금을 잡기 때문에, 앞에 오래 도는 쿼리가 있으면 그 뒤로 일반 `SELECT`까지 줄줄이 대기하면서 서비스가 멈출 수 있다. 항상 `SET lock_timeout = '5s';`처럼 잠금 대기 제한을 걸고 실행하며, 대용량 인덱스 생성도 `CREATE INDEX CONCURRENTLY` 같은 무중단 옵션을 써야 한다. 백업 역시 자동 백업 설정만 믿지 말고 실제로 복구 테스트를 한 번쯤 돌려봐야 한다.

## 2. 인프라

쿠버네티스나 오토스케일링보다 먼저 익혀야 할 건 서버가 어떤 환경에서 돌아가고, 어떻게 죽으며, 죽었을 때 어떻게 알아차릴 것인가다.

### 서버는 언제든 재시작되고 늘어난다

브라우저에선 전역 변수나 메모리에 상태를 둬도 탭이 닫히기 전까진 유지된다. 서버에서 같은 습관대로 짜면 바로 문제가 생긴다.

```ts
const sessions = new Map();    // 로그인 세션을 메모리에 저장
const uploadDir = "./uploads"; // 업로드 파일을 로컬 디스크에 저장
```

새로 배포하면 메모리는 초기화되고, 서버를 두 대로 늘리면 첫 요청은 1번 서버로, 다음 요청은 2번 서버로 가서 로그인이 풀려버린다. 서버리스 환경에선 요청마다 인스턴스가 새로 뜰 수도 있다.

서버 자체는 상태를 가지지 않게(stateless) 만들고, 세션·캐시는 Redis나 DB로, 파일은 S3 같은 외부 오브젝트 스토리지로 빼야 수평 확장이나 재시작에도 안전하다.

### 로컬·스테이징·운영 환경을 분리한다

최소한 로컬과 운영은 분리하고, 가능하면 운영과 동일한 구조의 스테이징 환경을 둔다. 로컬에서 운영 DB에 직접 붙어 개발하다 테스트 데이터 지운다는 게 실제 유저 데이터를 날리는 사고가 종종 난다. 운영 데이터를 수동으로 수정해야 할 땐 반드시 같은 `WHERE` 조건으로 `SELECT`를 먼저 실행해 대상 건수를 확인한 뒤 트랜잭션 안에서 실행한다.

### 외부 API 호출에는 반드시 타임아웃을 건다

결제, 메일, LLM API, 지도 API 등 외부 서비스는 언젠가 느려지거나 먹통이 된다. 타임아웃이 없으면 상대 서버가 응답을 안 줄 때 내 서버의 요청도 같이 멈춰 서고, 커넥션과 메모리가 고갈되면서 서비스 전체가 뻗는다. Node.js의 `fetch`는 기본 타임아웃이 길기 때문에 명시적으로 끊어줘야 한다.

```ts
const res = await fetch(url, { signal: AbortSignal.timeout(5000) }); // 5초 제한
```

재시도할 때는 바로 연달아 찌르지 말고 1초, 2초, 4초처럼 간격을 늘려가며(exponential backoff) 횟수를 제한해야 한다. 그리고 앞서 다룬 **멱등성**이 여기서도 중요하다. 결제 요청이 타임아웃 났다고 무조건 재시도하면, 실제로는 앞선 요청이 성공했을 경우 이중 결제가 발생한다.

### 오래 걸리는 작업은 요청 밖으로 뺀다

회원가입 시 환영 메일 발송, 이미지 썸네일 변환, 리포트 생성처럼 사용자가 즉시 결과를 기다릴 필요 없는 작업은 API 요청 흐름에서 분리해 작업 큐(BullMQ, AWS SQS, Inngest 등)로 넘긴다. 큐에 넣고 바로 응답을 내려준 뒤 별도 워커가 비동기로 처리하게 해야 API 응답 지연과 서버리스 타임아웃을 피할 수 있다.

### DB 커넥션 수를 관리한다

DB가 동시에 유지할 수 있는 커넥션 수는 제한돼 있다(PostgreSQL 기본 100개). 일반 서버는 커넥션 풀을 공유하지만, 서버리스 함수는 인스턴스가 뜰 때마다 새 커넥션을 맺는다. 트래픽이 몰려 함수가 수백 개 뜨면 DB 커넥션이 순식간에 동나면서 에러가 터진다. 서버리스 환경이라면 앞에 PgBouncer 같은 커넥션 풀러를 두거나 HTTP 기반 서버리스 드라이버를 사용해야 한다.

### 로그는 장애 났을 때 원인을 찾을 수 있게 남긴다

운영 환경의 로그는 문제가 터진 뒤에 열어본다. 나중에 추적할 수 있도록 최소한의 원칙을 지켜야 한다.

* **에러 삼키지 않기:** `catch (e) {}`처럼 비워두면 장애 흔적이 아예 사라진다. 처리 못 할 에러면 로그를 남기고 다시 던진다.
* **내부 에러 노출 금지:** 사용자에겐 일반적인 안내 문구만 보여주고, 스택트레이스나 SQL 에러 원문(테이블 구조 노출 위험)은 서버 로그에만 남긴다.
* **요청 ID(Request ID) 부여:** 요청 진입 시 고유 ID를 발급해 해당 요청에서 찍히는 모든 로그에 포함시키고 에러 화면에도 노출하면, CS 문의가 왔을 때 관련 로그를 한 번에 엮어 볼 수 있다.
* **구조화 로깅:** 단순 문자열 이어붙이기 대신 JSON 형태로 남겨야 검색과 필터링이 가능하다.

  ```ts
  logger.error({ requestId, userId, err }, "order creation failed");
  ```

### HTTP 상태코드를 정확히 내려준다

무조건 `200 OK`를 내려주고 응답 본문에 `{ success: false }`만 담아 보내는 API는 모니터링을 망가뜨린다. 로드밸런서, CDN, APM 도구는 상태코드를 기준으로 에러율을 집계하기 때문이다.

| 코드 | 의미 | 주요 상황 |
| --- | --- | --- |
| **400** | 잘못된 요청 | 필수 파라미터 누락, 형식 오류 |
| **401** | 인증 실패 | 비로그인, 토큰 만료 |
| **403** | 권한 없음 | 일반 유저의 관리자 API 호출 |
| **404** | 리소스 없음 | 존재하지 않는 게시글/주문 |
| **409** | 상태 충돌 | 이메일 중복 가입, 재고 상태 충돌 |
| **429** | 요청 과다 | Rate limit 초과 |
| **500** | 서버 오류 | 처리되지 않은 예외 |

`4xx`는 클라이언트 요청 문제, `5xx`는 서버 장애다. 알람은 `5xx`에 건다.

### 관측 가능성과 롤백 준비

사용자 문의를 통해 장애를 처음 알게 되면 이미 늦은 거다.

* **에러 추적:** Sentry 같은 도구로 미처리 예외와 스택트레이스를 실시간 수집한다.
* **헬스체크:** `/health` 엔드포인트를 두고 외부 업타임 모니터가 주기적으로 확인하게 한다.
* **기본 지표:** 응답 시간, `5xx` 비율, DB 커넥션 수, CPU/메모리의 평상시 기준선(baseline)을 익혀둔다.
* **롤백 연습:** 배포 직후 문제가 생겼을 때 이전 버전으로 되돌리는 방법과 소요 시간을 미리 확인해 둔다. 그리고 금요일 저녁 배포는 가급적 피한다.

## 3. 보안

프론트에서 아무리 꼼꼼하게 막아놔도, 공격자는 브라우저 화면이 아니라 `curl`이나 스크립트로 API를 직접 찌른다.

### 클라이언트 입력값은 절대 믿지 않는다

```bash
curl -X POST https://example.com/api/orders \
  -H "Cookie: sid=..." \
  -d '{"productId": 1, "price": 1, "quantity": -5}'
```

프론트 검증은 UX용이고, 서버 검증이 진짜 보안이다. `zod` 같은 스키마 검증기로 모든 입력의 타입과 범위를 서버에서 다시 검증한다. 특히 `price`나 `userId`처럼 서버가 이미 알고 있거나 세션에서 꺼내야 하는 값은 절대 클라이언트 payload에서 받지 않는다.

### 요청마다 소유권과 권한을 확인한다 (IDOR 방지)

```ts
// 위험한 코드: 로그인만 체크하고 남의 주문인지 확인 안 함
const order = await db.order.findUnique({ where: { id: params.id } });
return Response.json(order);
```

URL의 주문 번호만 바꿔서 남의 데이터를 조회하는 취약점(IDOR)은 초보 백엔드에서 가장 흔하게 터진다. 조회 조건에 반드시 현재 세션의 `userId`를 함께 걸어야 한다.

```ts
const order = await db.order.findFirst({
  where: { id: params.id, userId: session.userId },
});
if (!order) return new Response(null, { status: 404 });
```

남의 리소스에 접근했을 땐 `403` 대신 `404`를 내려주는 편이 해당 ID의 존재 여부조차 숨길 수 있어 안전하다. 프론트에서 삭제 버튼을 숨기는 건 UI 처리일 뿐이므로, 실제 API 핸들러에서 매번 권한을 검증해야 한다.

### 받을 필드만 받고, 줄 필드만 준다

`await db.user.update({ where: { id: session.userId }, data: await req.json() })`처럼 요청 body를 통째로 DB에 넘기면, 공격자가 `"role": "admin"`이나 `"points": 999999`를 슬쩍 끼워 넣었을 때 그대로 반영된다(Mass Assignment). 허용된 필드만 화이트리스트로 뽑아서 반영해야 한다.

응답 역시 마찬가지다. `user` 객체를 그대로 `Response.json(user)`로 내보내면 화면에 안 그리더라도 브라우저 네트워크 탭에서 `passwordHash`, 전화번호, 이메일이 다 보인다. ORM의 `select`로 처음부터 필요한 컬럼만 조회해 내려준다.

### SQL 인젝션 방지

문자열 템플릿으로 SQL을 조립하면 안 된다.

```ts
// 절대 금지
db.$queryRawUnsafe(`SELECT * FROM users WHERE email = '${email}'`);

// 파라미터 바인딩 사용
db.$queryRaw`SELECT * FROM users WHERE email = ${email}`;
```

정렬 기준(`ORDER BY`)처럼 파라미터 바인딩이 안 되는 컬럼명을 동적으로 받아야 할 때는, 서버에 정의된 허용 컬럼 배열(`['created_at', 'price']`)에 포함된 값인지 검증한 뒤 쿼리에 넣는다.

### 비밀 키와 민감 정보 노출 차단

* DB 비밀번호, API 키, JWT 시크릿은 환경 변수로 관리하고 `.env`는 `.gitignore`에 등록한다. 실수로 커밋했다면 파일만 지우지 말고 **반드시 키를 재발급**한다.
* Next.js의 `NEXT_PUBLIC_`, Vite의 `VITE_` 접두사가 붙은 환경 변수는 빌드 시 클라이언트 번들에 그대로 박히므로 비밀 값을 절대 넣지 않는다.
* 로그에도 요청 헤더(`Authorization`, `Cookie`)나 비밀번호 필드가 통째로 찍히지 않도록 마스킹(redact) 처리한다.

### CORS는 API 방화벽이 아니다

CORS는 브라우저가 다른 출처의 스크립트에 응답을 보여줄지 말지 결정하는 브라우저 보안 정책이다. `curl`이나 타 서버에서 날리는 직접 호출은 CORS와 무관하게 서버에 그대로 도달한다. API 보호는 인증과 인가로 해야 한다. 또한 귀찮다고 요청 `Origin`을 무조건 반사하면서 `Access-Control-Allow-Credentials: true`를 열면 CSRF류 공격에 노출되므로 허용 출처는 명시적 목록으로 고정한다.

### 호출 횟수·크기·비용 상한 설정

무제한으로 열린 API는 무차별 대입 공격(Brute-force)이나 봇의 표적이 된다. 특히 인증 문자(SMS) 발송이나 서버 측 LLM API 호출 엔드포인트가 뚫리면 하룻밤 사이에 수백만 원 청구서가 날아온다.

* IP·사용자별 Rate Limit 적용 (초과 시 `429` 응답)
* SMS, 이메일, LLM 호출 등은 사용자별 일일 한도 별도 설정
* 요청 body 크기 및 파일 업로드 용량 제한
* 클라우드 계정 예산 알림(Billing Alert) 설정

### 파일 업로드 보안

* 확장자나 `Content-Type` 헤더만 믿지 말고 서버에서 실제 파일 시그니처(Magic Number)를 확인하거나 이미지를 재인코딩한다.
* 사용자가 올린 원본 파일명을 경로에 그대로 쓰면 경로 탐색 공격(`../../etc/passwd`)에 당할 수 있으므로 서버에서 UUID 등으로 파일명을 새로 발급해 저장한다.
* 업로드된 파일(특히 HTML, SVG)이 메인 서비스와 같은 도메인에서 서빙되면 XSS 스크립트가 서비스 권한으로 실행될 수 있으므로 S3 등 별도 도메인에서 내려준다.

### 의존성 관리

`npm install`로 설치되는 수백 개의 패키지도 내 서버 권한으로 실행된다. `package-lock.json` 같은 lock 파일을 커밋해 환경을 고정하고, `npm audit`이나 Dependabot으로 취약점 알림을 켜둔다. 몇 줄로 짤 수 있는 간단한 기능은 외부 패키지를 줄이는 것도 방법이다.

## 4. 트래픽이 몰릴 때

### 평균이 아니라 p99를 본다

평균 응답 시간이 200ms라도 그 안에 3초 걸리는 요청이 1% 섞여 있으면, API를 여러 개 호출하는 페이지에선 열 명 중 한 명꼴로 느린 화면을 겪는다. 응답 시간은 평균 대신 상위 99% 기준인 **p99**로 봐야 한다.

또한 응답이 느려지면 동시 처리 중인 요청 수(`초당 요청 수 × 평균 응답 시간`)가 급증한다. 트래픽이 그대로여도 DB 쿼리가 0.1초에서 1초로 느려지면 동시 점유 커넥션이 10배로 불어나면서 PostgreSQL 기본 커넥션 한도(100개)를 넘어 서버가 뻗어버린다.

### 병목의 대부분은 DB에서 시작된다

서버는 stateless로 만들어뒀다면 인스턴스 대수를 늘리면 되지만, DB는 쉽게 늘리기 어렵다. 트래픽 부하를 줄일 땐 보통 다음 순서로 접근한다.

1. **슬로우 쿼리 튜닝 및 인덱스 추가:** 비용 대비 효과가 가장 크다.
2. **캐싱 도입:** 자주 읽히고 변경이 적은 데이터를 Redis 등에 캐싱한다.
3. **읽기 전용 복제본(Read Replica) 분리:** 조회 트래픽을 레플리카로 분산한다. 단, 복제 지연(replication lag)이 있으므로 방금 쓴 직후 바로 읽어야 하는 데이터는 원본(Primary) DB에서 읽는다.
4. **DB 스펙 업그레이드(Scale-up):** 구조 개선으로 안 되면 장비 사양을 올린다.

### 캐시는 무효화와 만료 스탬피드까지 설계한다

```ts
async function getProduct(id: string) {
  const cached = await redis.get(`product:${id}`);
  if (cached) return JSON.parse(cached);

  const product = await db.product.findUnique({ where: { id } });
  await redis.set(`product:${id}`, JSON.stringify(product), "EX", 60);
  return product;
}
```

캐시는 넣는 것보다 지우는 게 어렵다. 상품 가격을 수정했을 때 기존 캐시 키를 삭제(invalidate)하지 않으면 60초 동안 옛날 가격이 노출된다. 결제 직전 금액 검증처럼 절대 틀리면 안 되는 값은 캐시가 아니라 DB에서 직접 읽어야 한다.

또한 인기 페이지의 캐시 키가 만료되는 순간 수천 개의 요청이 동시에 캐시 미스를 겪으며 DB로 한꺼번에 몰리는 **캐시 스탬피드(Cache Stampede)** 현상도 조심해야 한다. TTL에 약간의 무작위 시간(Jitter)을 더해 만료 시점을 분산시키거나, 뮤텍스 락을 걸어 요청 하나만 DB를 조회해 캐시를 채우도록 구성한다.

### 예고된 트래픽 급증 대비

앱 푸시 발송 직후나 선착순 이벤트 정각에는 평소의 수십 배 트래픽이 몇 초 만에 꽂힌다. 오토스케일링은 새 인스턴스가 뜨는 데 몇 분이 걸려 이 순간을 못 버틴다.

* 마케팅/기획 팀과 푸시·이벤트 일정을 미리 공유받는다.
* `k6` 같은 도구로 예상 트래픽의 몇 배 수준으로 사전 부하 테스트를 돌린다.
* 이벤트 시작 전에 미리 서버 인스턴스를 증설해 두고 끝나면 줄인다.
* 정적/공통 응답은 CDN에 캐싱해 오리진 서버 부하를 차단한다.
* 선착순 재고는 원자적 `UPDATE`로 처리하고, 감당 안 되는 트래픽은 앞단에 대기열을 둔다.

### 다 살릴 수 없으면 부가 기능부터 끈다

한계치를 넘기면 모든 요청이 느려지다 같이 죽는다. 그전에 핵심 기능만 살리는 선택을 해야 한다.

* **기능 플래그(Feature Flag):** 추천, 자동완성, 조회수 집계 같은 부가 기능은 설정값 하나로 즉시 끌 수 있게 만든다.
* **Fail Fast:** 감당 못 할 요청은 대기시키지 말고 바로 `429`나 `503`으로 거절해 나머지 정상 요청을 살린다.
* **서킷 브레이커(Circuit Breaker):** 외부 서비스 장애가 계속되면 일정 시간 동안 호출을 차단하고 기본값(fallback)을 반환해 연쇄 장애를 막는다.
* **중첩 재시도 금지:** 클라이언트(3회) → API 서버(3회) → DB(3회) 식으로 계층마다 재시도를 걸면 장애 상황에서 부하가 3 × 3 × 3 = 27배로 증폭된다. 재시도는 한 계층에서만 수행한다.

## 5. 장애가 났을 때

### 원인 분석보다 복구가 우선이다

알람이 울리면 궁금하더라도 디버깅부터 파고들면 안 된다. 사용자 입장에선 서비스 정상화가 1순위다. 가장 먼저 확인할 건 **"방금 뭐가 바뀌었나"**(배포, 환경 설정 변경, 마이그레이션, 트래픽 급증, 외부 API 장애)다. 직전에 배포가 있었다면 확신이 없어도 일단 롤백한다. 롤백해서 해결되면 원인이 좁혀지고, 안 돼도 배포 문제는 배제할 수 있다. 상세 원인 분석은 서비스를 살린 뒤에 로그를 보며 천천히 하면 된다.

### 조용히 혼자 고치지 않고 타임라인을 남긴다

장애가 발생하면 즉시 팀 채널에 전파하고, 여러 명이 붙을 땐 한 명이 상황 지휘(Incident Commander)를 맡아 역할을 나눈다. 각자 따로 서버를 재시작하다 상황이 더 꼬이는 걸 막기 위해서다.

조치 내역은 시간과 함께 실시간으로 기록한다.

```text
14:05 결제 API 5xx 급증 확인
14:08 직전 배포(v2.31) 롤백 시작
14:12 롤백 완료, 에러율 정상 복구
```

이 기록은 장애가 길어질 때 중복 작업을 막아주고, 사후 회고의 타임라인이 된다. 필요하다면 상태 페이지나 공지로 사용자에게도 지연 사실을 안내한다.

### 운영 환경에서는 급할수록 천천히 움직인다

장애 중 당황해서 운영 DB에 직접 `UPDATE`를 날리거나 서버 설정을 급히 고치다 2차 장애를 내는 경우가 많다. 운영 명령은 동료에게 한 번 더 교차 확인을 받고, 데이터 수정은 반드시 `SELECT` 확인 후 트랜잭션 안에서 실행한다.

### 새벽 3시를 위한 런북(Runbook)

새벽에 알람을 받고 깨면 판단력이 떨어진다. 자주 발생하는 알람별로 확인 순서와 대응 명령어를 적어둔 **런북**을 미리 만들어 둔다.

```text
[알람: DB 커넥션 사용률 90% 초과]
1. 대시보드에서 최근 배포 및 트래픽 급증 여부 확인
2. 장기 실행 쿼리 조회:
   SELECT pid, now() - query_start AS duration, query
   FROM pg_stat_activity WHERE state = 'active' ORDER BY duration DESC;
3. 병목 쿼리 강제 종료: SELECT pg_cancel_backend(pid);
4. 직전 배포가 있었다면 즉시 롤백
```

### 회고(Postmortem)는 사람이 아니라 구조를 고친다

장애 종료 후 타임라인, 영향 범위, 근본 원인, 재발 방지 대책을 정리한다. 이때 "누가 실수했나"를 추궁하기 시작하면 다음 장애 때 사람들이 실수를 숨기게 된다. 누군가 운영 DB 테이블을 잘못 지웠다면, **한 사람이 실수로 지울 수 있었던 권한과 시스템 구조**를 고쳐야 한다. "앞으로 주의하자"는 대책이 아니다.

**DB**

* [ ] 중복·필수값·범위 제약은 `UNIQUE`, `NOT NULL`, `CHECK`, FK로 DB에 걸었는가?
* [ ] 함께 성공/실패해야 하는 작업은 트랜잭션으로 묶고, 내부에서 외부 API를 빼냈는가?
* [ ] 읽고 계산해 덮어쓰는 코드를 원자적 `UPDATE`나 행 잠금(`FOR UPDATE`)으로 바꿨는가?
* [ ] 결제·생성 요청에 `Idempotency-Key`로 중복 처리를 막았는가?
* [ ] 쿼리 로그로 N+1을 잡았고, 느린 쿼리는 `EXPLAIN ANALYZE` 확인 후 인덱스를 걸었는가?
* [ ] 목록 API에 개수 제한과 커서/페이지네이션을 적용했는가?
* [ ] 금액은 정수/`NUMERIC`, 시간은 UTC(`timestamptz`)로 저장하는가?
* [ ] 무중단 스키마 변경 단계를 지켰고, 백업 복구 테스트를 해봤는가?

**인프라**

* [ ] 서버 메모리·디스크에 상태를 두지 않고 Redis/DB/오브젝트 스토리지로 분리했는가?
* [ ] 로컬·스테이징·운영 DB가 분리되어 있는가?
* [ ] 모든 외부 API 호출에 타임아웃이 걸려 있고, 재시도는 멱등한 요청에만 적용했는가?
* [ ] 오래 걸리는 부가 작업은 작업 큐로 분리했는가?
* [ ] 서버리스 환경이라면 DB 커넥션 풀러를 연결했는가?
* [ ] 에러를 삼키지 않고, `requestId`가 포함된 구조화 로그를 남기는가?
* [ ] HTTP 상태코드를 규약대로 내려주고 `5xx`에 알람을 걸었는가?
* [ ] 에러 추적(Sentry), 헬스체크, 기본 지표 모니터링과 롤백 절차가 준비돼 있는가?

**보안**

* [ ] 모든 입력을 서버에서 재검증하고, 가격·`userId` 등 신뢰할 수 없는 값은 클라이언트에서 안 받는가?
* [ ] 모든 리소스 접근 시 세션 사용자 소유권과 권한을 서버에서 확인하는가?
* [ ] 허용된 필드만 업데이트하고, 응답에도 필요한 필드만 선택해 내려주는가?
* [ ] Raw SQL에 문자열 결합 대신 파라미터 바인딩을 썼는가?
* [ ] 비밀 키가 Git, 프론트 번들(`NEXT_PUBLIC_` 등), 로그에 노출되지 않는가?
* [ ] CORS 허용 출처를 명시적으로 고정하고 인증/인가를 구현했는가?
* [ ] Rate Limit, 비용 발생 API 일일 한도, 요청 크기 제한, 클라우드 예산 알림을 걸었는가?
* [ ] 업로드 파일의 실제 포맷 검증, UUID 파일명 변경, 별도 도메인 서빙을 적용했는가?
* [ ] Lock 파일을 커밋하고 의존성 보안 취약점 알림을 활성화했는가?

**트래픽 & 장애 대응**

* [ ] 평균이 아닌 `p99` 지연 시간을 모니터링하고, 서버 증설 전 DB 쿼리부터 점검하는가?
* [ ] 캐시 무효화 시점과 만료 스탬피드(Jitter/Lock)를 고려했는가?

* [ ] 장애 시 원인 분석보다 롤백을 먼저 검토하고, 타임라인 기록과 런북·포스트모템 문화를 갖췄는가?
